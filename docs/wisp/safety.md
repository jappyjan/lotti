# Wisp — brick safety policy

The G2 has a single-slot main app, no rollback, and its BLE + OTA live in that app ([hardware.md](hardware.md#boot-and-update-chain-stock)). **An image that crashes before BLE is up turns a temple into an SWD-only repair.** This file is the rulebook. It overrides convenience, deadlines and every other Wisp document.

## Hard rules (no exceptions, enforced in tooling)

1. **Never write** the Ambiq SBL (`0x400000–0x410000`), the Even bootloader (`0x410000–0x438000`), or anything at or past `0x7FE000` except the documented update-flag record ([hardware.md](hardware.md#update-flag-record-0x7fe000-16-bytes): `{0x55555555, ~0, ~0, ~0}` = install, `{~0 ×4}` = clear, written through the boot-ROM helper like stock does). Wisp tooling refuses to build such an image. On the device, Wisp Boot's only MRAM writes are the install record and, after a new install, the documented clear record (R4-3), both through one function with a constant address; rung 3 checks this from the boot-ROM log in every case. The native app links no MRAM write path at all.
   **Single exception (W18, Jan 2026-11-06):** one install per temple of drdaeman's patched bootloader (pinned, see [recovery.md](recovery.md)), left temple first, each with its own explicit go (rule 4). Nothing else ever writes the bootloader region. The image is pinned at SHA-256 `87e2d4e0a7a673ae…` (155,648 B). The only tool that sends it is `apps/wisp-recovery/w18.py bootloader-install`, which refuses any other image, needs the per-side `--go` token, and enforces the preconditions in [recovery.md, W18 procedure](recovery.md#w18-procedure). Its loader tools write MRAM only inside the main-app region `[0x438000, 0x7F8000)`, with one of two images: (i) the pinned stock main image (`recover`), or (ii) a Wisp native image (`install-wisp`) whose SHA-256, ELF and map hashes are pinned in `wisp_w18/pins.py` by a reviewed commit; the tool re-runs every rule-3 check in both implementations on the exact bytes it sends; its first 64 KiB (Wisp Boot) are byte-identical to a build that passed its rung-3 suite on the stock 2.4.0.24 **and** the patched `87e2d4e0…` bootloader; and `check_rule8.py` and the no-MRAM-write gate over `[0x448000, end)` pass. Both kinds zero the 16 vector bytes first and write them last. Besides these images the loader may write one thing more: the documented **clear** record of the update flag, only by calling the bootloader's own `bootloader_error_reset` from a pinned program (`flag-clear`). Each write needs its own go (rule 4) naming the image hash. The tools refuse in code the install value of the flag, the bootloader region and everything at or past `0x7F8000`. No write runs unless `loader-hello` has read the bootloader CRC `63cd8dda` and a clear flag in the same session (`flag-clear` excepted; `recover` keeps `--allow-pending-flag`, because recovery is exactly when the flag may be set). *(Extended by R4-1, Jan 2026-11-08; details in [rung4.md](rung4.md#3-how-it-gets-onto-the-temple).)*
2. **Never send** component types 1 (bootloader), 3 (touch), 4 (codec), 5 (EM9305) or 6 (case). Wisp bundles are **main-only** (type 0). `wisp-ota` rejects anything else.
3. Main-app image checks, all in `wisp-ota`, all mandatory: load address `0x438000`; preamble size = payload size; app end ≤ `0x7F8000`; SP vector points into SRAM; reset vector inside the image and Thumb; both CRC layers recomputed and re-verified by an independent second implementation.
4. **No flash without an explicit, per-flash "go" from the hardware owner (Jan)** in chat. An earlier "go" never covers a later flash. Agents never flash on their own initiative, never on a schedule.
5. **One temple at a time, left first.** The right temple stays on stock until the left one has passed a full round trip (flash → boots → reflash stock over BLE → boots).
6. Before every flash, by setup (R4-4, Jan 2026-11-08):
   - **BLE flash:** battery > 80 %, temples out of the case, nothing on the table that can bump them, only the flashing phone near, Even app force-quit.
   - **Case session (loader writes):** the temple seated, the lid open, the case on USB, the Mac on its charger with `caffeinate`; battery ≥ 80 % read in the Even app while on stock, or ≥ 3,900 mV from Wisp's status while native (threshold to be confirmed against stock's 80 % at W21).
7. Keep the exact stock bundle for the installed version (SHA-256 pinned) available offline before the first flash.
8. **Never let firmware reflash a co-processor.** Ambiq's Zephyr EM9305 driver (`am_devices_em9305_init()` in hal_ambiq `am_devices_em9305.c`) erases and reflashes the EM9305's NVM when the device version is older than **or equal to** the bundled `ble_fw_image_em9305.h` (equal = CRC-verify, reflash on mismatch), when the version can't be read, and when the controller fails to boot — unless the caller sets `skip_fw_update`. Even ships its own EM9305 build, so that would wipe or brick the radio. On the fork (`ambiq-stable` 89c8a36) **no caller sets it safely**: the HCI driver `apollox_blue.c` leaves it `false` whenever `CONFIG_BT` is on, and the evb's `board.c` EXTREF init (`CONFIG_SOC_APOLLO510B_EM9305_EXTREF_INIT`, default y whenever the HCI node is enabled) sets it to `IS_ENABLED(CONFIG_BT)`, i.e. `false` when BT is off. `skip_fw_update` is also only a runtime flag: the 234 KB image and the erase/write code stay linked even when it is set. Wisp therefore carries a patch to the fork (`apps/wisp-fw/third_party/ambiq/`, applied by `wisp-fw:setup`) that compiles the update, recovery, configuration-mode and NVM-trim paths out of the driver, drops the bundled image, forces `skip_fw_update = true` for every caller and stops sending the public-address vendor command (persistence undocumented). A Bluetooth build fails at configure time unless the exact patch is in both projects, and after every link unless the image proves it: the driver and its callers preprocessed with their real compile commands, symbols, map sections, instruction immediates and the raw image bytes (see `apps/wisp-fw/README.md`, "Checks in place"). `wisp-fw:test` builds against pristine trees to show both gates fire. The same applies to the PSoC touch controller and the GX8002 codec: Wisp never contains their firmware images.
9. **Never commit Even's firmware** (copyright). Stock bundles are fetched or copied into a git-ignored local cache (`.wisp-cache/`), pinned by SHA-256; tests use synthetic bundles.
10. Never copy GPL code into Wisp (licensing, not bricking — but it is a rule too). Facts and offsets from GPL projects are fine with credit.
11. **No native flash without a proven way back to stock on that temple** (R4-2, Jan 2026-11-08). Before every native write: case recovery (W18 F2) has passed on that temple, the held-temple reset test has passed, and `loader-hello` passes in the same session as the write, before it.
    A verified `wisp/rescue.bin` is **also** required before the forced-fault test, before any native install over BLE (together with a `flag-clear` proven on that temple), and before a native temple is used away from the case and the Mac. Verified means: size, preamble and zlib CRC equal the pinned stock main payload of the installed version, as checked on the temple by Wisp Boot's own rescue check and reported over BLE or the case UART.
12. **Every change to Wisp Boot reruns `wisp-fw:boot-test`** (rung 3), on the stock 2.4.0.24 and the patched `87e2d4e0…` bootloader, before it may be flashed; a native image is only flashed with a Wisp Boot whose build passed it. (R4-7, Jan 2026-11-08: Wisp Boot may change after W17 for the observe-only build, the status block, the PMIC kick, the flag clear and the image-keyed record.)

## Fallback-to-stock (designed into native mode)

The Even bootloader installs whatever valid main image is staged in `ota/s200_firmware_ota.bin` when word 0 of the flag is `0x55555555` ([hardware.md](hardware.md#what-the-22610-bootloader-does-step-by-step-rung-3)). Wisp uses that as its parachute:

1. Before the first native flash, the phone stores a pristine stock main image on the NOR littlefs as `wisp/rescue.bin` (written through the stock OTA file path while still on stock, or by Wisp host mode; neither exists: 2.4.0.24's OTA receiver refuses any path but the component type's own, and host mode was dropped. [rung4.md](rung4.md#5-rule-11-rescuebin) proposes writing it through Wisp itself) and **verifies it on the glasses** (size, preamble, CRC) — see rule 11.
2. **Wisp Boot**, a tiny stage at `0x438000` (the image's entry), runs before anything else: it counts boot attempts in a record on the NOR (`wisp/boot.rec`), and if the app failed to confirm 3 boots in a row (or the touchpad rescue hold is seen at boot), it copies `wisp/rescue.bin` to `ota/s200_firmware_ota.bin`, verifies the copy's CRC, writes the flag record and resets. The Even bootloader then installs stock. A rescue interrupted by a power cut resumes on the next boot.
3. The native app confirms a boot only after BLE is advertising and a phone session completed `HELLO`. A watchdog, armed and locked by Wisp Boot, covers hangs.

Wisp Boot is small (16.8 KB: MSPI NOR PIO driver, littlefs, CRC, one flag write, watchdog), changes rarely, and is fault-tested in Renode against the real bootloader before it ever runs on glasses (rung 3, `pnpm nx run wisp-fw:boot-test`, [apps/wisp-fw/README.md](../../apps/wisp-fw/README.md#rung-3-fallback-to-stock-with-the-real-even-bootloader-wisp-fwboot-test)). Everything else in the native image may crash and the temple comes back as stock.

Verified in rung 3 (was "still to verify"): the flag record (only word 0 is read; hardware.md), that the bootloader rereads the staged file after an interrupted install (yes: the flag stays set until the app clears it, and the install restarts from the file), and the littlefs geometry on the NOR.

What fallback-to-stock **cannot** do (terminal states):

- With `rescue.bin` missing or corrupt, Wisp Boot never stages it and never writes the flag; the Wisp app keeps booting (degraded every third boot). Without a working BLE path in that app this is an SWD-only repair. Rule 11 exists for this. (Rung 3 cases `rescue-corrupt`, `rescue-missing`.)
- After 4 rescue attempts that did not end in stock, Wisp Boot stops resetting and runs the app degraded. (Host unit tests only: no rung-3 case makes the real bootloader refuse a verified copy.)
- A crash inside Wisp Boot before it records the attempt loops forever. Not injected in rung 3. Hence: Wisp Boot stays minimal, has no BLE and no interrupts, and every change to it reruns rung 3 (rule 12).

### Rung 1 status (2026-11-06)

**Passed on the left temple (2026-11-06)**, full round trip over BLE from the Lotti Wisp update screen, each flash with Jan's own go: repack 2.4.0.29 → success, boots, Lotti and the Even app work → pure stock 2.4.0.24 back → success, the right temple reports left 2.4.0.24 again. This also proved on hardware that the glasses accept the return to a lower version string. The right temple was never flashed. Facts from before the flash, kept for reference: both temples run stock **2.4.0.24** (right temple, sid `0x09`, battery 94 %). Rung 1 therefore repacks 2.4.0.24, and the return trip sends pure 2.4.0.24. 2.4.0.24 is pinned in `catalog.ts` (SHA-256 `363198f8…`, Even's CDN), so `wisp-ota fetch 2.4.0.24` satisfies rule 7 on any machine.

- Guards: `verify` on the stock bundle: valid, not sendable (it carries types 1, 3–6). `repack-main --version 2.4.0.29` (the iOS default) or `2.4.0.25`: **sendable**, every guard passes, and `diff` is clean (10 version strings, the two CRC layers, nothing else). App end `0x7BF564`, 226.7 KiB below the ceiling. The flag address and ceiling are the same as on 2.2.6.10, so no guard needed a per-version constant.
- What changed vs 2.2.6.10 ([hardware.md](hardware.md#stock-24024-installed-on-jans-temples)): the bootloader's install path is instruction-identical and has no version check. The OTA receiver has the same reply set, but RESULT_CHECK now re-reads the staged file before it answers. A slow readback (> 8 s) makes the sender report `result-unknown`, which is a safe outcome (reconnect and read the version), and a 90 s idle watchdog applies.
- Downgrades: no version check was found in the bootloader or in the app's OTA receiver. The return trip to 2.4.0.24 from 2.4.0.29 is a downgrade by version string, so the first rung-1 round trip also tests that on hardware. If the glasses refused it, the temple would stay on the repack. That is stock code, so it is not a brick, but it is not pure stock either.
- **Never install a main app older than 2.2.9.22** until the NOR part of both temples is known. Older apps drive only the MX25U25643G.

Emulation only (t3-worker, Renode), stock bootloader running unmodified, Wisp Boot `8dd8fd69ef4b…`: **26/26 runs end in their expected state, on the 2.2.6.10 bootloader and on 2.4.0.24's** (the version on Jan's temples; same build of Wisp Boot, same verdict and end state in every case) (table in [apps/wisp-fw/README.md](../../apps/wisp-fw/README.md#rung-3-fallback-to-stock-with-the-real-even-bootloader-wisp-fwboot-test)). A corrupt or missing `rescue.bin` ends in the documented safe state instead (no flag, Wisp keeps booting). In every run the bootloader region is unchanged and Wisp's only MRAM write is the flag record.

**Not called passed yet.** Open before Jan signs rung 3 off: review of the terminal states and rules 11–12; which bootloader is actually in MRAM (the 2.4.0.24 suite assumes the bundle's own; 2.3.2.14's DFU code is identical to it, [hardware.md](hardware.md#bootloader-24024-vs-22610)) and whether the temples' NOR is the MX25U25643G the model emulates or the GD25LE256H that bootloaders since 2.2.9.22 also drive; the real native app (Zephyr) behind Wisp Boot instead of bare-metal fault apps. Model limits that stay (README "What Renode lacks"): NOR/MRAM operations are atomic (no cut inside a page program or erase), no core lockup, no SBL, SRAM pessimistically lost on every reset.
